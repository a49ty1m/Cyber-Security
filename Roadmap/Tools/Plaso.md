# ⏱️ Plaso / log2timeline: Complete Mastery Checklist

> **What is Plaso?** Plaso (Plaso Langar Að Safna Og) is the engine behind `log2timeline` — a framework for super-timeline creation in digital forensics. It extracts timestamp-based events from hundreds of artifact types (Registry hives, event logs, browser history, prefetch files, LNK files, NTFS journal, email, etc.) across Windows, Linux, and macOS, and consolidates them into a single chronological timeline (called a plaso storage file, `.plaso`), which can then be filtered, converted, and queried with `psort`.
>
> **Why does it exist?** Manual timeline reconstruction across multiple artifact types is slow and error-prone. Plaso automates the extraction of every timestamp-bearing artifact from a disk image and merges them into a unified, searchable timeline. This is critical for incident response — identifying an attacker's first action, last action, and sequence of activities across heterogeneous evidence sources.
>
> **When to use it:** Building a super-timeline from a disk image during incident response. CTF forensics timeline challenges. Correlating disparate artifact timestamps (Registry vs. browser history vs. event logs) into a single view.
>
> **What mastering Plaso unlocks:** Automated super-timeline creation. Evidence correlation across artifact types. Efficient incident reconstruction. Foundation for Phase 7 Part 27 Stage 4 (Network Forensics) and Stage 6 (Advanced Analysis & Reporting).
>
> **Roadmap Phase:** Phase 7 Part 27 (Digital Forensics)

# PHASE 1: INSTALLATION & ARCHITECTURE

---

## 1.1 Installation

```bash
# Install via pip (recommended for Python 3)
pip3 install plaso

# Or Docker (avoids dependency conflicts — recommended for complex environments)
docker pull log2timeline/plaso
docker run -v /evidence:/evidence log2timeline/plaso log2timeline --help

# Verify installation
log2timeline.py --version
psort.py --version
pinfo.py --version

# List all available parsers
log2timeline.py --parsers list

# List all output modules (export formats)
psort.py --output list
```

- [ ] **Architecture — Three Tools:**
  - **`log2timeline.py`:** Extracts timestamps from evidence and writes them to a Plaso storage file (`.plaso`). This is the slow step — it reads every artifact.
  - **`psort.py`:** Sorts, filters, and exports the `.plaso` storage file to human-readable formats (CSV, JSON, l2tcsv, xlsx). This is the analysis step.
  - **`pinfo.py`:** Displays metadata about a `.plaso` storage file — what parsers ran, how many events were extracted, storage file creation time.

- [ ] **Plaso Storage File (`.plaso`):** A SQLite database containing serialised event objects from all extracted artifacts. Do not edit this file directly — use `psort` for all queries.

---

## 1.2 Parser Categories

- [ ] **Windows Parsers:** Registry (`winreg`), Event Logs (`winevtx`), Prefetch (`winprefetch`), LNK files (`lnk`), Jump Lists (`olecf_automatic_destinations`), Shellbags (`msie_webcache`), MFT (`mft`), USN Journal (`usnjrnl`), Recycle Bin (`recycler`, `esedb`)

- [ ] **Browser Parsers:** Chrome (`chrome_history`, `chrome_cookies`), Firefox (`firefox_history`, `firefox_downloads`), Edge (`msie_webcache` — Chromium-based Edge uses Chrome format), IE (`msie_webcache`)

- [ ] **Email Parsers:** Outlook PST (`pst`), Thunderbird MBOX (`text_file` with pattern recognition)

- [ ] **Linux/macOS Parsers:** syslog, bash_history, utmp, apt history, macOS unified log (`.logarchive`), macOS plist files, bash/zsh history files

- [ ] **File System Parsers:** `mft` (NTFS MFT), `usnjrnl` (USN Change Journal), `filestat` (file system stat — last modified/accessed for all files)

# PHASE 2: log2timeline — EVIDENCE INGESTION

---

## 2.1 Basic Usage

```bash
# Process an entire disk image (auto-detects parsers)
log2timeline.py case.plaso /path/to/disk.E01

# Process a specific partition (if image has multiple partitions)
log2timeline.py --partitions 2 case.plaso /path/to/disk.dd

# Process only specific parsers (faster, targeted)
log2timeline.py --parsers winevtx,winprefetch,lnk,mft,usnjrnl case.plaso /path/to/disk.E01

# Process a mounted image directory (e.g., after mounting E01 with ewfmount)
log2timeline.py case.plaso /mnt/image/

# Add timezone for the evidence system (CRITICAL — affects all timestamp display)
log2timeline.py --timezone America/New_York case.plaso /path/to/disk.E01

# Verbose output (useful for debugging parser failures)
log2timeline.py --debug case.plaso /path/to/disk.E01

# Process with worker processes for speed (default: CPU count / 2)
log2timeline.py --workers 4 case.plaso /path/to/disk.E01
```

- [ ] **Timezone Setting:** The `--timezone` flag sets the timezone for interpreting local timestamps in evidence artifacts. Always determine the evidence system's timezone before running log2timeline. Getting this wrong shifts all timestamps.

- [ ] **Parser Selection:** Running all parsers on a large drive is slow (hours). For targeted investigations, select only relevant parsers. For full forensic analysis, run all parsers and filter later with psort.

- [ ] **Evidence Types:** log2timeline accepts: raw disk images (`.dd`, `.img`), E01 images, directory trees, ZIP archives, single files. For mounted images, provide the mount point directory.

- [ ] **Storage File Appending:** You can run log2timeline multiple times against different evidence sources and append to the same `.plaso` file with `--append`. Useful for combining disk image and memory artifacts.

- [ ] **Hasher Configuration:** `--hasher md5,sha256` — computes hashes for files during parsing. Stored in the plaso file and available in psort output. Allows correlation with known malware hashes.

---

## 2.2 Parser-Specific Notes

- [ ] **`mft` Parser:** Extracts MACB timestamps for every file in the MFT. This creates the largest artifact set — expect millions of events for typical Windows installations. Essential for complete timeline but slows processing significantly.

- [ ] **`usnjrnl` Parser:** The USN Change Journal records file operations (create, modify, rename, delete) with timestamps. Valuable for reconstructing attacker file activity even after file deletion.

- [ ] **`winevtx` Parser:** Parses Windows Event Log `.evtx` files. Extracts Event IDs with full record content. For incident response, filter on security event IDs: 4624 (logon), 4625 (failed logon), 4688 (process creation), 4698 (scheduled task created), 7045 (service installed).

# PHASE 3: psort — TIMELINE FILTERING & EXPORT

---

## 3.1 Basic psort Usage

```bash
# Export full timeline to CSV (l2tcsv format)
psort.py -o l2tcsv -w timeline.csv case.plaso

# Export to JSON
psort.py -o json -w timeline.json case.plaso

# Export with time filter (incident window)
psort.py -o l2tcsv -w filtered.csv case.plaso "date > '2026-01-01 00:00:00' AND date < '2026-01-03 23:59:59'"

# Filter by hostname (if multiple systems in plaso file)
psort.py -o l2tcsv -w output.csv case.plaso "hostname is 'WORKSTATION01'"

# Filter by data type (e.g., only Windows Event Logs)
psort.py -o l2tcsv -w events.csv case.plaso "data_type is 'windows:evtx:record'"

# Filter by keyword in event description
psort.py -o l2tcsv -w output.csv case.plaso "message contains 'cmd.exe'"

# Combine filters with AND/OR
psort.py -o l2tcsv -w output.csv case.plaso "date > '2026-01-01' AND message contains 'powershell'"
```

- [ ] **l2tcsv Format:** The standard Plaso CSV output format with columns: `date, time, timezone, MACB, source, sourcetype, type, user, host, short, desc, version, filename, inode, notes, format, extra`. Use this format for Timeline Explorer or Excel analysis.

- [ ] **Timeline Explorer (Eric Zimmerman):** Load the l2tcsv output into [Timeline Explorer](https://ericzimmerman.github.io/#!index.md) (free Windows GUI tool). Filter by date, event type, keyword, and colour-code suspicious entries. Essential companion to Plaso for investigation.

- [ ] **Event Filtering Strategy:** For investigations, work backwards from known indicators:
  1. Filter timeline to ±24 hours around known compromise timestamp
  2. Search for attacker tooling names (mimikatz, nc.exe, cobalt, beacon)
  3. Search for suspicious process names in `data_type:windows:evtx:record` entries
  4. Correlate with Registry persistence keys (HKCU/HKLM Run, scheduled tasks)
  5. Look for lateral movement indicators (NTLM authentication events from unusual source IPs)

# PHASE 4: pinfo & STORAGE ANALYSIS

---

```bash
# Display storage file metadata
pinfo.py case.plaso

# Show which parsers ran and their event counts
pinfo.py --sections parsers case.plaso

# Show storage file statistics
pinfo.py --sections storage case.plaso
```

- [ ] **Verifying Parser Coverage:** Run `pinfo.py --sections parsers` to confirm all expected parsers ran successfully. If a critical parser (e.g., `mft`, `winevtx`) shows 0 events, investigate — the evidence may lack that artifact or the parser encountered an error.

- [ ] **Event Count Sanity Check:** A typical Windows disk image yields: 1–10M events from MFT filestat, 100k–1M from Event Logs, 10k–100k from Registry, 1k–10k from browser/prefetch/LNK. Significantly lower counts indicate parsing issues.

- [ ] **Storage File Inspection:** The `.plaso` file is a SQLite database. For debugging: `sqlite3 case.plaso ".tables"` shows internal table structure. Do not modify the file — use psort for all queries.

# PHASE 5: TIMELINE ANALYSIS WORKFLOW

---

## 5.1 Investigation Workflow

- [ ] **Step 1 — Anchor on Known Events:** Identify timestamps you already know — malware execution time from AV logs, user report of anomaly, network IDS alert time. These are your anchors. Filter the Plaso timeline to a window around each anchor.

- [ ] **Step 2 — Expand the Window:** Start with ±1 hour around each anchor. Identify the earliest attacker-related event. Expand backwards to find initial access. Expand forward to find persistence, lateral movement, exfiltration.

- [ ] **Step 3 — Artifact Correlation:** For each suspicious event, look for corroborating artifacts. A suspicious Prefetch entry → look for Registry run key created at similar time → look for file creation in temp directory → look for network connection event (from Volatility memory if available).

- [ ] **Step 4 — Negative Evidence:** Note what is ABSENT. No logon event in Security log for a claimed time period. No browser history during a time when a user claims to have been browsing. No Prefetch entry for a claimed program execution. Absence of expected artifacts is evidence.

# PHASE 6: PRACTICAL LABS

---

- [ ] **Basic Timeline Lab:** Process a forensics CTF disk image with log2timeline. Export to l2tcsv with psort. Open in Timeline Explorer or LibreOffice Calc. Filter to identify the top 10 most suspicious events and write a 1-paragraph investigation summary.

- [ ] **Incident Window Lab:** Given a disk image with a known compromise (CyberDefenders "DFIR" challenge), use Plaso to build a timeline. Filter to the 48-hour window around the compromise. Identify: initial access artifact, persistence mechanism, lateral movement attempt, data staging path.

- [ ] **Multi-Source Correlation Lab:** Combine Plaso super-timeline (disk artifacts) with Volatility network connections (memory) and Wireshark PCAP timestamps. Correlate events across all three timelines to reconstruct an attacker's complete sequence of actions.

- [ ] **Reporting Lab:** From a complete Plaso timeline, write a formal incident timeline report: executive summary, timeline table (timestamp | artifact type | description | significance), IOC list, and recommendations. This is the deliverable format for Phase 7 capstone and client-facing reports.

## 📝 Operational Notes

- **Processing speed:** log2timeline takes 1–6+ hours for a typical 256 GB Windows drive. Run overnight for large acquisitions. Use `--workers` to maximize CPU utilisation.
- **Timezone is critical:** Wrong timezone shifts all timestamps. Always verify: `SYSTEM\CurrentControlSet\Control\TimeZoneInformation` in the Registry, or check system locale artifacts in the image before running log2timeline.
- **Parser updates:** Plaso is actively developed. Run `pip3 install --upgrade plaso` periodically. New parsers are added regularly (new browser formats, new Windows artifact types).
- **Filtering first, then export:** Do NOT export the full timeline to CSV for a large image — millions of rows are unmanageable. Always filter to an incident window with `psort` query first.
- **Integration with Elastic:** For large investigations, import Plaso output directly into Elasticsearch with `psort -o elastic` and query with Kibana. This enables sub-second search across multi-million event timelines.
- **Complement with Autopsy:** Plaso provides the timeline; Autopsy provides file content. Use Plaso to identify suspicious timestamps, then use Autopsy to examine file content at those timestamps.
